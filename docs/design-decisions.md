# Design decisions and trade-offs

Each entry gives the decision, what was rejected, and why.

## Local evaluation for servers, remote evaluation for browsers

**Server SDKs** download all rules and evaluate in-process: microseconds per call, no
network dependency on the hot path, and the app keeps working if the flag service is down.
The cost is that SDKs in different languages must agree exactly, which is why the spec and
shared vectors came first.

**Browser SDKs** can't do this: anything sent to a browser is public, and rules contain user
lists, internal attributes and the names of unreleased features. So the browser sends the
user to `/sdk/v1/evaluate` and receives only the values of flags explicitly marked
`client_side`. The client-side ID is public by design and can't fetch rules (tested). The
browser's live channel carries only "something changed" pings.

## Server-Sent Events, not WebSockets or polling

- Updates are one-directional (server → SDK), which is exactly what SSE is.
- SSE is plain HTTP: it works through proxies, load balancers and nginx (with buffering off, see
  `dashboard/nginx.conf`), and needs no upgrade handshake.
- Polling makes a trade between latency and load: 30-second polling means a kill switch takes 30
  seconds. Both SDKs still offer polling as a fallback mode.

Streams send a heartbeat every 15 s, and SDKs treat 45 s of silence as a dead connection. That
catches connections that die without a TCP close.

## Versioning: two counters

- `flag_configs.version`, per flag per environment, is used for **optimistic concurrency**
  in the editor (If-Match / 409).
- `environments.data_version`, per environment, is used to **order the stream**. Each change
  gets the next number. An SDK at version 41 that receives 43 knows it missed 42 and
  re-fetches the snapshot instead of drifting silently.

The increment is an `UPDATE … RETURNING` inside the change's transaction. Its row lock
serializes writers per environment, so versions commit in order without a global lock.

## Postgres LISTEN/NOTIFY for fan-out, not Redis

Multiple API processes must all learn about every change. NOTIFY is transactional (delivered
only on commit, in commit order) and needs no extra infrastructure. The payload is tiny
(org, environment, version). The listener reads the exact change from `sdk_change_log`, so
large flags don't hit NOTIFY's 8 KB limit and a listener can never see uncommitted data.

The limit is that every process holds one extra connection and does one small read per change.
At very large scale (hundreds of API processes) a dedicated broker, or a relay tier between
the API and SDKs, would be the next step.

If the listener's own connection drops, it reconnects and tells every local stream to close.
Their SDKs reconnect and receive fresh snapshots, so changes made during the gap are never lost.

## Snapshot on every (re)connect

The stream always starts with a full `put`. This is simpler and more robust than replaying
history since `Last-Event-ID`: no retention window to size, and no edge cases when the window
is exceeded. Snapshots are small (a few KB per hundred flags). The change log is therefore
only needed for milliseconds and is trimmed to the last 1,000 versions per environment.

The stream subscribes *before* reading the snapshot. A change that commits in between is
already queued, and the SDK discards it as stale if the snapshot already includes it. Nothing
can fall into the gap.

## Never break the host app

Every public SDK method takes a default and catches everything. Failures are reported in
the evaluation *reason* (`CLIENT_NOT_READY`, `FLAG_NOT_FOUND`, `WRONG_TYPE`,
`MALFORMED_FLAG`, `USER_NOT_SPECIFIED`, `EXCEPTION`), never thrown. Initialization waits a
bounded time and never fails. Listeners that throw are isolated. Event buffers drop instead of
growing. `close()` is idempotent and returns immediately: the Python SDK shuts the socket under
a blocked read, because `HTTPResponse.close()` from another thread would wait for the read
timeout (a real bug, found by the test suite taking 45 s).

## No regex operator

Python and JavaScript regex dialects differ: lookbehind support, Unicode classes, and
catastrophic backtracking behaviour. A `matches` operator would break the identical-answers
guarantee and allow ReDoS through targeting rules. `starts_with`, `ends_with`, `contains`,
`in`, numeric and semver operators cover typical targeting.

Unknown operators evaluate as non-matching rather than as errors, so an old SDK keeps working
if the server adds operators later. The API, however, rejects unknown operators on save.

## Identical answers across languages

- **Shared vectors** (`spec/test-vectors/`): 111 hand-written cases whose expected values are
  stated, not generated by an engine. Both SDKs run them.
- **Differential fuzzing** (`scripts/cross_sdk_fuzz.py`): 20,000 random flags × users, both
  engines, exact comparison. This is in CI.
- Language traps are written into the spec. Booleans aren't numbers (Python's `True == 1`).
  Integral floats bucket like ints. Attributes are own properties only: in JS,
  `user["constructor"]` is a function, which would make `constructor is not "x"` match. A
  vector now pins that. SHA-1 is implemented in pure TS so evaluation stays synchronous in
  browsers and edge runtimes.

## Concurrency: optimistic, with a human in the loop

Locking a flag while someone edits it fails badly: people leave tabs open. Instead every save
says "I edited version N". On conflict the dashboard shows *theirs vs yours* and the user
chooses: load theirs, or deliberately overwrite. Nothing is silently lost. Toggles in the
list view use the same mechanism.

## Audit trail in the same transaction

The audit row is added to the same session as the change and commits with it, so a change
without an audit entry is impossible, and so is an entry for a change that rolled back
(tested). The runtime DB role has `UPDATE`/`DELETE` revoked on `audit_log`, so even an
application bug can't rewrite history.

## SDK keys

Server keys are random 192-bit tokens stored as SHA-256 hashes. A slow KDF isn't needed for
high-entropy secrets, and a fast hash keeps per-request lookup cheap. They're shown once.
Rotation can keep the old key valid for a grace period so services can be redeployed without an
outage. Client-side IDs are stored in plain text because they're public anyway.

## Experiments: what makes results trustworthy

The arithmetic is easy; the traps are not:

- **Broken assignment** (bots, a redirect that drops one arm, a config change mid-test)
  shows up as a sample-ratio mismatch. With SRM, *no* result is shown as significant.
- **Peeking**: checking daily and stopping at the first p < 0.05 inflates false positives
  several-fold. Results are inconclusive until a sample size chosen in advance is reached.
  (A sequential test, such as mSPRT, would allow safe continuous monitoring and is the natural next step.)
- **Many comparisons**: with 3 treatments at α = 0.05 the chance of a false winner is about 14%.
  Bonferroni keeps it at 5% (conservative, but simple and honest).
- **Post-exposure only**: purchases before a user saw the variation can't be caused by it.

## What I'd do next

- Segments (reusable user groups) and scheduled changes / approval workflows for production.
- A relay proxy tier for very large SDK fleets, and per-SDK-key connection limits.
- Rate limiting in Redis when there's more than one API process (the current limiter is in-process).
- Sequential testing for experiments; CUPED variance reduction.
- Generated TypeScript types from the OpenAPI schema instead of hand-written ones.
